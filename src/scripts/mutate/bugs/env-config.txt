# How NANOBENCH_CONFIG is parsed and reaches a Bench. The whole point of the
# variable is that a number typed into a shell arrives at the right setting with
# the right value, so every bug here is one that would leave a benchmark running
# with settings nobody asked for - and unlike a wrong measurement, there is no
# output that says so. Run with a sweep over the same code for what is not
# listed here:
#
#     mutate.py --bugs src/scripts/mutate/bugs/env-config.txt \
#               --lines 2673-2930 --reuse
#
# A snapshot against the code as it was: when a block stops applying, that part
# has been rewritten and these questions want re-deriving rather than repairing.

# The setter is bypassed for the field behind it, so a rule the setter enforces
# stops holding for a value that arrived from the environment -
# minEpochIterations stops refusing 0.
#
# This one is caught by the compiler, and that is the point of it: Bench::config()
# hands out a `Config const&`, so there is no way to reach the fields from here at
# all. The route through the setters is structural rather than remembered, which
# is a better answer than a test.
<<<
    if (reason.empty()) {
        (bench.*setter)(static_cast<Arg>(parsed));
    }
    return true;
}
